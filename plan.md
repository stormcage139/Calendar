# План реализации курсового проекта — сервис совместного планирования

## 1. Цель проекта

Разработать веб-сервис для совместного планирования встречи, поездки или другого события. Создатель формирует событие и варианты дат/мест, приглашает участников, а участники отмечают занятость и голосуют. Система находит наиболее подходящее общее окно, подсчитывает результаты и фиксирует итоговое событие.

Срок реализации: **1 месяц (4 недели)**.

## 2. Текущий стек и его развитие

В проекте уже используются:

| Часть | Технологии |
|---|---|
| Backend | Python, FastAPI, Uvicorn |
| Работа с БД | SQLAlchemy Async, asyncpg, Alembic |
| База данных | PostgreSQL |
| Frontend | React 19, TypeScript, Vite |

Для реализации понадобятся дополнительно:

- `pydantic-settings` — конфигурация приложения;
- `PyJWT` или `python-jose` и `passlib[bcrypt]` — регистрация, вход и JWT-аутентификация;
- `httpx` (frontend можно оставить на `fetch`) — запросы к API;
- по необходимости `APScheduler` — автоматическое закрытие голосований и напоминания;
- Docker Compose — единый запуск frontend, backend и PostgreSQL (желательно, но можно оставить на последнюю неделю).

## 3. Границы MVP

За месяц следует реализовать полностью работающий **MVP**, а не пытаться покрыть все расширения.

### Обязательная часть MVP

1. Регистрация, вход и профиль пользователя.
2. Создание, редактирование, отмена и просмотр событий.
3. Приглашение зарегистрированных участников и по уникальной ссылке.
4. Добавление вариантов даты и места.
5. Внесение занятых интервалов участников.
6. Поиск общего свободного окна среди предложенных дат.
7. Голосование «за / против / нейтрально» за даты и места.
8. Автоподсчёт результата, обработка ничьей и ручное закрытие голосования создателем.
9. Отображение статусов участников и истории событий.
10. Базовые уведомления внутри приложения.

### Оставить как дополнительные задачи

- Ранжированное голосование.
- Реальный чат и WebSocket-обновления.
- Email-уведомления и сложные фоновые напоминания.
- Экспорт в iCalendar (`.ics`).
- Публичные события, подробная статистика, интеграции с внешними календарями.

Если обязательная часть готова раньше срока, дополнения лучше делать именно в таком порядке: `.ics` → ранжированное голосование → email/планировщик → чат.

## 4. Основные сущности базы данных

| Сущность | Главное содержимое |
|---|---|
| `users` | логин, email, хеш пароля, имя, часовой пояс |
| `events` | название, описание, тип, создатель, дедлайн, статус, настройки голосования |
| `event_members` | событие, пользователь/гостевой токен, роль, статус приглашения, время ответа |
| `invite_links` | событие, уникальный токен, срок действия, лимит использований |
| `date_options` | событие, начало и конец интервала, автор, комментарий |
| `place_options` | событие, название/адрес, автор, комментарий |
| `availability` | участник, событие, начало и конец занятого интервала |
| `votes` | участник, вариант, тип голоса (`for`, `against`, `neutral`) |
| `results` | утверждённые дата и место, способ разрешения, время фиксации |
| `notifications` | получатель, тип, текст, состояние прочтения |

Статусы события: `draft` → `collecting_options` → `voting` → `completed`; отдельно допустимы `cancelled` и `archived`.

## 5. Ключевой алгоритм: поиск общего окна

Для MVP используется понятный и проверяемый подход:

1. Все даты и интервалы хранятся в UTC, а на интерфейсе отображаются в часовом поясе пользователя.
2. Для каждого предложенного диапазона собираются занятые интервалы всех участников.
3. Диапазон разбивается на равные слоты (например, 30 минут или 1 час).
4. Для каждого слота считается число свободных участников.
5. Объединяются соседние слоты с одинаковой доступностью.
6. В результат выводятся окна, где свободны все участники; если таких нет — окна с максимальным числом свободных.

Формат результата, например: «12 октября, 14:00–17:00 — свободны 4 из 5 участников». Это прозрачно для демонстрации и достаточно для небольшого числа участников курсового проекта.

## 6. План на 4 недели

### Неделя 1 — фундамент и управление событиями

**Цель недели:** получить запускаемое приложение с пользователями, базой данных и CRUD событий.

Backend:

- Настроить конфигурацию через `.env`, подключение к PostgreSQL и Alembic.
- Создать модели `User`, `Event`, `EventMember` и первую миграцию.
- Реализовать регистрацию, вход, JWT и зависимость текущего пользователя.
- Реализовать API событий: создать, список моих событий, просмотр, редактирование создателем, отмена/архивация.
- Добавить проверку прав: редактирование и закрытие доступны только создателю.
- Написать базовые тесты API аутентификации и событий.

Frontend:

- Настроить структуру проекта: API-клиент, типы, роутинг, хранение токена.
- Сделать страницы: вход/регистрация, список событий, создание и карточка события.
- Добавить формы с валидацией и состояния загрузки/ошибок.

Результат недели: пользователь входит в систему, создаёт событие и видит его в личном списке.

### Неделя 2 — участники, варианты и занятость

**Цель недели:** участники могут присоединиться к событию и подготовить данные для голосования.

Backend:

- Добавить модели и миграции: `InviteLink`, `DateOption`, `PlaceOption`, `Availability`.
- Реализовать приглашение пользователя и создание ссылки-приглашения.
- Реализовать гостевое присоединение по токену; предусмотреть отображаемое имя гостя.
- Реализовать добавление/удаление вариантов дат и мест, комментариев к ним.
- Реализовать добавление, изменение и удаление занятых интервалов участника.
- Добавить API списка участников и их статусов.
- Покрыть сценарии прав доступа и присоединения тестами.

Frontend:

- На странице события сделать вкладки «Участники», «Варианты», «Занятость».
- Реализовать форму приглашения и экран принятия приглашения.
- Реализовать формы добавления дат (день или диапазон), мест и комментариев.
- Реализовать удобный список занятых интервалов; сложный календарный drag-and-drop не обязателен.

Результат недели: группа может создать событие, пригласить людей, предложить даты/места и указать занятость.

### Неделя 3 — алгоритм, голосование и итог

**Цель недели:** сделать главную ценность сервиса — выбор общей даты и результата голосования.

Backend:

- Реализовать сервис `availability_service` с алгоритмом поиска доступных временных окон.
- Добавить API расчёта окон, сортировку по числу свободных и длительности.
- Создать модели `Vote` и `Result`, подготовить миграцию.
- Реализовать переход к голосованию, подачу и изменение голоса.
- Реализовать подсчёт баллов: `за = +1`, `нейтрально = 0`, `против = -1`.
- Реализовать ручное и автоматическое по дедлайну закрытие голосования.
- При ничьей сохранить список лидеров и дать создателю выбрать победителя (без повторного раунда в MVP).
- Написать unit-тесты алгоритма, подсчёта голосов, ничьей и прав доступа.

Frontend:

- Добавить визуальное представление доступности: таблицу «участник × предложенная дата/окно».
- Показать рекомендуемые окна и объяснение «свободны N из M».
- Реализовать экран голосования за даты и места.
- Реализовать страницу результата и действие создателя при ничьей.

Результат недели: сервис находит оптимальное окно, проводит голосование и фиксирует итоговую дату и место.

### Неделя 4 — качество, уведомления и подготовка защиты

**Цель недели:** довести MVP до состояния демонстрации и сдачи.

Backend:

- Добавить модель/API `Notification` и внутрисистемные уведомления: приглашение, новый вариант, завершение голосования, итог.
- Проверить автоматическое закрытие голосований: фоновая задача либо проверка дедлайна при обращении к событию.
- Добавить историю завершённых событий и настройку часового пояса профиля.
- Настроить CORS, обработку ошибок, логирование и OpenAPI-описание.
- Достичь покрытия критических сервисов и API тестами.
- При возможности подготовить Docker Compose и инструкцию запуска.

Frontend:

- Добавить список уведомлений и отметку о прочтении.
- Отполировать адаптивность, пустые состояния, сообщения об ошибках и доступность форм.
- Провести ручное тестирование полного сценария несколькими пользователями.

Документация и защита:

- Обновить README: установка, переменные окружения, запуск, миграции, тесты.
- Подготовить ER-диаграмму БД, диаграмму компонентов и схему алгоритма поиска окна.
- Подготовить 5–7-минутный сценарий демонстрации: создать событие → пригласить участников → добавить занятость/варианты → проголосовать → показать результат.
- Сформировать список известных ограничений MVP и направлений развития.

Результат недели: приложение разворачивается по инструкции, проходит основной пользовательский сценарий и готово к показу.

## 7. Порядок выполнения задач внутри спринта

Каждую задачу стоит вести по одной цепочке:

1. Уточнить пользовательский сценарий и API-контракт.
2. Создать модель SQLAlchemy и миграцию Alembic.
3. Реализовать бизнес-логику в `services`.
4. Реализовать репозиторий и маршруты FastAPI.
5. Написать backend-тесты для обычного и ошибочного сценариев.
6. Добавить TypeScript-типы, API-вызовы и экран React.
7. Проверить сценарий вручную от начала до конца.

Так не появится интерфейс, который ожидает ещё не существующий или другой API.

## 8. Распределение задач в команде

Если в команде 3 человека, удобно разделиться так:

| Роль | Основная зона ответственности | Дополнительно |
|---|---|---|
| Участник 1 — backend | модели, миграции, API событий/участников, авторизация | тесты и документация API |
| Участник 2 — алгоритмы/backend | доступность, голосование, подсчёт результата, уведомления | unit-тесты сервисов |
| Участник 3 — frontend | страницы, формы, API-клиент, таблицы доступности и голосование | UX, ручное тестирование, презентация |

Общие правила:

- В начале каждой недели согласовывать DTO/JSON-контракты в OpenAPI.
- Проводить короткий общий созвон или проверку раз в 2–3 дня.
- Не смешивать в одном pull request несвязанные функции.
- К концу каждой недели должна быть демонстрируемая вертикальная функция, а не только набор моделей или макетов.

## 9. Критерии готовности MVP

Проект можно считать готовым, если демонстратор может:

1. Зарегистрировать двух пользователей и создать событие.
2. Пригласить второго пользователя по ссылке или напрямую.
3. Добавить несколько дат, мест и занятых интервалов.
4. Увидеть рекомендованное общее окно и доступность участников.
5. Открыть голосование, проголосовать с двух аккаунтов и изменить голос до дедлайна.
6. Закрыть голосование, получить победившие дату/место и обработать ничью.
7. Увидеть итог в истории и уведомление внутри приложения.

## 10. Основные риски

| Риск | Как снизить |
|---|---|
| Слишком большой объём функций | Следовать границам MVP; дополнительные функции брать только после готовности обязательных. |
| Сложность календарного интерфейса | Начать с обычных полей даты/времени и таблицы; визуальный календарь добавить только при запасе времени. |
| Ошибки часовых поясов | Хранить все временные метки в UTC, преобразовывать только при отображении. |
| Конфликты в коде команды | Разделить области файлов, работать в ветках, заранее согласовывать API-контракты. |
| Неясные правила ничьей | Для MVP: создатель выбирает среди лидеров; правило явно показать на интерфейсе. |

## 11. Минимальная структура backend

```text
backend/src/backend/
├── api/v1/routers/       # auth, events, invitations, availability, voting
├── core/                 # config, security
├── db/                   # сессия, базовый класс
├── models/               # SQLAlchemy-модели
├── repositories/         # запросы к БД
├── schemas/              # Pydantic DTO
├── services/             # правила предметной области и алгоритмы
└── main.py
```

Такое разделение позволит не размещать алгоритм поиска окон и подсчёт голосов непосредственно в маршрутах API.
