# Подключение frontend к существующему FastAPI

Изменения ограничены `frontend/`. Оформление, CSS и графические ресурсы сохранены.
Planner использует реальные данные после проверки сессии, включая прямой переход
на `#calendar`. Статическая иллюстрация на странице входа остаётся примером.

## Используемые контракты

Все пути ниже указаны без клиентского префикса `/api`, который удаляет Vite proxy.

| Метод и путь | Использование | Ответ |
| --- | --- | --- |
| `POST /register` | Регистрация, JSON `{ login, email, password }` | `{ id, login, email }`, 409 при дубликате |
| `POST /login` | Вход, JSON `{ login, password }` | `{ access_token, token_type: "bearer" }` |
| `GET /me` | Проверка сессии и профиль | `{ id, login, email }` |
| `GET /events/` | Список, поиск, календарь, история | `[{ id, name, online, deadline }]` |
| `POST /events/` | Создание из существующего диалога | `{ id, name, online, deadline }` |
| `GET /friends` | Друзья | `[{ id, login, email }]` |
| `GET /friends/requests` | Входящие и исходящие заявки | `[{ new_freind_id, type: "incoming" \| "outgoing", accepted_date }]` |
| `POST /friends/{id}` | Отправить или принять заявку | `true`, `false` или `{ error }` |
| `DELETE /friends/{id}` | Удалить друга, отменить или отклонить заявку | `true` или `false` |
| `PATCH /users/{id}` | Изменить свой профиль | `{ user: { id, login, email, ... } }` |
| `DELETE /users/{id}` | Удалить свой аккаунт | `{ deleted: boolean }` |
| `GET /ping` | Проверка соединения | `"pong"` |

Опечатка `new_freind_id` сохранена в чтении ответа backend и преобразуется во
внутреннее `friend_id`. `type` определяет направление заявки; принятые заявки
исчезают из списка ожидающих. Ответы `false` и `{ error }` не считаются успехом.
Друзья убираются из повторов по ID; собственный профиль исключается из отображения.
Заявка отправляется непосредственно по введённому положительному целому ID.
Свой ID пользователь видит в профиле. Для имён используются только данные списка
друзей; неизвестные участники заявок отображаются как `ID N`.
Отладочный список пользователей `/users/all` не используется.

Событие отправляется как `{ name, online, deadline: "YYYY-MM-DDT00:00:00" }`.
Ответ POST сразу добавляется в список, затем выполняется GET для синхронизации.
Backend хранит `deadline` в колонке `Date`: календарь показывает дни, без времени.
Разделы «Активные» и «Прошедшие» группируют события по дедлайну, а не по отсутствующему
в ответе статусу. Архив показывает прошедшие дедлайны с явной пометкой о недоступности
архивирования.

Для PATCH обязательны все поля `{ login, email, password }`. Frontend предлагает
ввести текущий или новый пароль. Backend хэширует пароль; клиент считывает только
публичные поля ответа. После успешного сохранения сессия закрывается и предлагается
повторный вход: JWT использует логин как subject. Удаление аккаунта требует ввода
своего логина в диалоге. Клиент использует только ID текущего профиля.

## In progress в интерфейсе

Существующие области интерфейса без рабочих контрактов показывают точную надпись
**In progress**, а действия сохранения/отправки отключены:

- категории, описание и диапазон дат события;
- приглашения участников, ссылки-приглашения и список участников;
- занятость, предложения дат/мест, голосование и результаты;
- обсуждение события и личные сообщения;
- архивирование события;
- настройки часового пояса, уведомлений и голосования;
- уведомления о событиях (в колокольчике доступны реальные заявки в друзья).

`invite_links.py` содержит незавершённый `/mylinks` и не включён в FastAPI app.
Клиент не обращается к нему. Также отсутствуют маршруты редактирования и удаления
событий. Frontend не имитирует сохранение неподдерживаемых данных в localStorage.

## Оставшиеся ограничения backend

- Маршруты PATCH и DELETE `/users/{id}` в текущем backend не проверяют
  авторизацию. Клиент отправляет токен и ограничивает изменение своим ID, но проверку
  доступа должен обеспечивать сервер.
- PATCH возвращает ORM-пользователя, включая хэш пароля. Клиент исключает это поле
  из своего результата; backend следует возвращать только публичную схему.
- Ошибки PATCH могут возвращать `{ user: null }` с HTTP 200; клиент показывает ошибку,
  не сообщает о сохранении и не закрывает форму.
- Добавление друга на сервере не проверяет существование получателя. Клиент проверяет
  формат ID и запрещает добавлять себя; существование получателя должен проверять backend.
- Backend может повторять друзей и включать текущего пользователя при нескольких
  связях. Клиент фильтрует эти записи.
- Время, автор, роль, участники и статус события не входят в текущую схему ответа.
  В интерфейсе не показываются вымышленные значения этих полей.

## Проверки

`npm test` проверяет контракты API, обработку ошибок/сессии, календарные границы и отправку заявки по ID.
`npm run test:integration` запускает неизменённое FastAPI приложение с временной
SQLite в памяти и проверяет регистрацию, конфликт регистрации, вход, профиль,
события и изоляцию между аккаунтами, оба направления заявок,
принятие/отклонение/удаление, изменение профиля с повторным входом и удаление аккаунта.
Исходники backend и его пользовательская база не изменяются.
