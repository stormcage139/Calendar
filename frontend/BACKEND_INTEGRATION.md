# Подключение frontend к существующему backend

Изменения сделаны только в `frontend`. Исходники, настройки и пользовательская
база backend не изменялись. Оформление входа и регистрации сохранено; вместо
заглушки после входа добавлено рабочее пространство в той же палитре.

## Подключённые эндпоинты

| Метод и путь | Использование на frontend | Текущий ответ |
| --- | --- | --- |
| `POST /users` | Регистрация | JSON-строка `user created ...` |
| `POST /token_test` | Вход с OAuth-формой `username`, `password` | `{ access_token, token_type }` |
| `GET /users/me/` | Профиль, проверка и восстановление сессии | `{ id, login, email }` |
| `GET /events/` | Календарь по дням и список всех событий | `[{ id, name, online, deadline }]` |
| `POST /events/` | Создание события, затем повторное чтение списка | `null` |
| `GET /friends` | Список друзей | `[{ id, login, email }]` |
| `GET /friends/requests` | Входящие и исходящие заявки | `[{ from_user, to_user, accepted_date }]` |
| `POST /friends/{id}` | Отправка заявки и принятие встречной заявки | `true`, `false`, либо `{ error }` при добавлении себя |
| `DELETE /friends/{id}` | Удаление друга, отклонение входящей и отмена исходящей заявки | `true` или `false` |
| `DELETE /users/{id}` | Удаление своего аккаунта с подтверждением логином | `{ deleted: boolean }` |
| `GET /ping` | Кнопка проверки соединения в профиле | JSON-строка `pong` |

Авторизованные запросы отправляют `Authorization: Bearer <access_token>`.
Токен хранится в `sessionStorage`; пароли не сохраняются. При ответе 401 сессия
сбрасывается и появляется форма входа. При недоступности профиля токен сохраняется
для повторной попытки. Ошибки разных списков показываются независимо.

Сейчас API возвращает `token_type: "bearer"`: формат уже подходит клиенту,
дополнительное поле `type` не требуется.

## Что необходимо изменить или добавить в backend

Ниже формулировки для разработчика backend. Эти изменения не внесены.

1. В логике авторизации на POST `/token` должны использоваться поля `login` и
   `password` JSON-объекта, нужно передавать `form_data.login` и
   `form_data.password` в `authenticate_user` вместо `*form_data.model_config`.
   Сейчас корректный запрос возвращает 500. Frontend использует рабочий
   POST `/token_test`.

2. В логике получения пользователя на GET `/users/{id}` должен приходить
   структурированный пользователь, нужно возвращать
   `{"user":{"id":1,"login":"name","email":"name@example.com"}}`
   вместо `{"user":"id:1 / login: name / email: ..."}`, а для отсутствующего
   пользователя возвращать HTTP 404 вместо строки `"None"`.
   Frontend не разбирает эту строку и не использует этот эндпоинт.

3. В логике заявок на GET `/friends/requests` нужны данные участников для
   отображения имён, нужно добавить отдельные поля `from_user_profile` и
   `to_user_profile` с объектами `{ id, login, email }`, сохранив числовые
   `from_user` и `to_user`. Сейчас неизвестные участники отображаются по ID;
   получить их имена по существующему структурированному API нельзя.

4. В логике изменения профиля на PATCH `/users/{id}` пароль должен сохраняться
   хэшированным, нужно хэшировать новый `password` перед записью и исключить
   пароль из ответа. Сейчас обработчик сохраняет открытый пароль и возвращает
   его в `user.password`; следующий вход завершается ошибкой 500.
   Редактирование профиля и смена пароля на frontend не подключены.

5. В логике изменения и удаления аккаунта на PATCH и DELETE `/users/{id}`
   должна проверяться авторизация и принадлежность аккаунта, нужно использовать
   текущего пользователя и возвращать HTTP 403 при обращении к чужому ID.
   Оба существующих обработчика не требуют токен. Frontend отправляет токен
   и позволяет удалить только ID своего профиля, но серверную проверку этим
   заменить нельзя. Для удаления также нужно определить очистку связанных
   событий, участников и дружеских связей: текущий код не задаёт эту политику.

6. В логике событий на POST и GET `/events/` время должно сохраняться без потери,
   нужно согласовать `deadline` схемы (`datetime`) с полем БД (`Date`). Сейчас
   запрос с `2026-10-16T18:30:00+03:00` после сохранения возвращает
   `2026-10-16T00:00:00`. Frontend предлагает только дату и отправляет её как
   `YYYY-MM-DDT00:00:00`. Для календаря встреч с часовыми интервалами нужны
   отдельные `starts_at` и `ends_at` с часовым поясом; в текущем API их нет.

7. В логике списка друзей на GET `/friends` должны возвращаться только друзья
   текущего пользователя без повторов, нужно исключать все вхождения своего
   ID, а не только первое. Сейчас при нескольких дружеских связях собственный
   пользователь может попасть в ответ. Frontend убирает повторы по ID и
   исключает свой профиль при отображении.

8. В логике отправки заявки на POST `/friends/{id}` должна проверяться
   существующая учётная запись получателя, нужно возвращать HTTP 404 для
   отсутствующего пользователя. Сейчас такой проверки нет; при выключенных
   внешних ключах SQLite возможно создание связи с несуществующим ID, после
   чего GET `/friends` может не сериализовать `None`. Для повторной заявки и
   прочих отказов нужны различимые коды/поле `detail`: текущее `false` не
   сообщает причину, поэтому frontend показывает общий текст ошибки.

9. В логике регистрации на POST `/users` должна проверяться уникальность логина
   и email, нужно добавить соответствующие ограничения и HTTP 409 для
   конфликта. В текущих модели и миграции ограничений уникальности нет;
   проверок в обработчике также нет. Frontend обрабатывает 409, если сервер
   начнёт его возвращать. Регистрация уже хэширует пароль; прежняя заметка
   README об отсутствии хэширования больше не соответствует исходникам.

10. В логике авторизации на POST `/token_test` ошибка `authenticate_user` должна
    завершать обработчик корректно, нужно исключить использование переменной
    `user`, которой не присвоено значение после исключения. Сейчас повреждённый
    пароль в БД приводит к дополнительному `UnboundLocalError` и HTTP 500.

11. Для редактирования и удаления событий нужны PATCH/DELETE `/events/{id}` с
    проверкой прав, а для приглашения и ответа участников нужны отдельные
    эндпоинты. Сейчас в маршрутах событий доступны только чтение и создание;
    `create_invite_to_event` в репозитории содержит `pass`. Управление
    участниками, редактирование и удаление событий не имитируются на клиенте.

12. Для добавления друзей по логину нужен эндпоинт поиска пользователей с
    ответом `[{ id, login, email }]`. Сейчас поиск отсутствует, поэтому
    добавление реализовано по ID, доступному в профиле каждого пользователя.

Категории «Работа / Друзья / Личное», место встречи, длительность и участники
на календаре страницы входа остаются иллюстрацией. В существующих схемах событий
этих данных нет; рабочий календарь показывает только реальные поля API.

## Проверка

- `npm run build` — TypeScript и production-сборка.
- `npm run lint` — проверка frontend.
- `npm test` — восемь проверок API-клиента: форматы, токен, HTTP-ошибки,
  отмена запросов, сетевые ошибки, `false` при HTTP 200, списки и даты.
- `npm run test:integration` — реальные запросы frontend-клиента к неизменённому
  backend на временном localhost-порту и SQLite в памяти. Проверены регистрация,
  вход, профиль, события, изоляция событий между пользователями, дружба,
  принятие/отмена/отклонение заявок, удаление аккаунта, истечение сессии и ping.
  Отдельно воспроизведены неисправный `/token`, строковый GET пользователя,
  потеря времени и неисправный PATCH профиля.

Тестовый процесс выполняется во временном каталоге, использует `python -B` и
подменяет только зависимость БД в памяти процесса. Миграции и реальная база
не используются. Это не проверка пользовательской БД или production-развёртывания.
Визуальная проверка в браузере не выполнялась: доступных браузерных сессий нет.
